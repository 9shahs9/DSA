LEARNINGS FROM DOUBLY LINKED LIST PARTITION TESTS
=================================================

1. TAIL POINTER IN DUMMY NODE PATTERN
   Issue: partition_list_dummy_nodes was setting self.tail = r_dummy unconditionally,
   which caused tail to point to the dummy node (value 0) when no elements went to the
   right partition.
   
   Fix: Conditionally set tail based on which partition has elements:
        self.tail = r_dummy if d2.next else l_dummy
   
   Learning: When using dummy nodes for partitioning, the tail must always point to
   the actual last data node, not a dummy node.


2. EDGE CASE HANDLING IN PARTITIONING ALGORITHMS
   Critical edge cases for partition methods:
   
   a) All elements in left partition (all < x)
      - Right dummy remains unchanged with no next pointer
      - Left partition should end with the last left element
      - Tail should point to last left element, not the dummy
   
   b) Single element lists
      - Must correctly identify if element goes left or right
      - Head and tail should point to the same node (when only one element remains)
      - Must handle the case where that single node is the only data node
   
   c) Mixed partitions with both left and right elements
      - Must correctly link left partition's last node to right partition's first node
      - All bidirectional links must be valid throughout


3. BIDIRECTIONAL LINK INTEGRITY IN DOUBLY LINKED LISTS
   When modifying doubly linked lists:
   
   a) Never create orphaned pointers
      - Always update BOTH next and prev when inserting/reconnecting nodes
      - Test both forward and backward traversal to catch broken links
   
   b) Validity checks at boundaries
      - Always set head.prev = None (head has no predecessor)
      - Always set tail.next = None (tail has no successor)
      - These are critical for boundary traversals
   
   c) Breaking previous links when moving nodes
      - When a node is removed from one list and added to another,
        clear its old links (node.prev = None, node.next = None) if appropriate
      - Or update all connecting nodes (node.prev.next, node.next.prev)


4. COMPREHENSIVE TEST COVERAGE STRATEGY
   The partition test suite covers:
   
   a) Basic functionality: normal mixed partition scenario
   b) Extreme cases: 
      - All elements in one partition
      - Single element in list
   c) Structural integrity:
      - Bidirectional link validity (forward + backward traversal match)
      - Head/tail boundary conditions
      - Length preservation
   d) Order preservation:
      - Relative order of elements within each partition is maintained


5. DUMMY NODE PATTERN ADVANTAGES
   The dummy node approach (partition_list_dummy_nodes) compared to flag-based 
   approach (partition_list):
   
   Advantages:
   - Eliminates need for left_init and right_init flags
   - Simplifies the logic by avoiding special-case handling for head insertion
   - More elegant and less error-prone code structure
   - Dummy nodes provide a consistent "previous" pointer for all real nodes
   
   Considerations:
   - Must correctly handle the final tail pointer assignment
   - Must ensure dummy nodes never appear in the final data structure
   - Must null-check before accessing dummy's children


6. NULL POINTER CHECKS IN LIST ALGORITHMS
   Critical points for null-safety:
   
   a) Before dereferencing pointers:
      if d2.next:  # Before accessing d2.next.prev
          d2.next.prev = l_dummy
   
   b) After linking operations:
      if self.head:  # Before setting head.prev = None
          self.head.prev = None
   
   c) When traversing:
      Always check if curr is not None before accessing curr.next or curr.value


7. PARTITION METHOD BUGS IN NON-DUMMY IMPLEMENTATION
   The original partition_list method had a bug:
   Line: self.append(right_curr.next)  # WRONG - should be right_curr.value
   
   This demonstrates the importance of:
   - Carefully reviewing loop variable usage
   - Testing edge cases that would catch such bugs
   - Using similar test assertions for alternative implementations


8. TESTING PHILOSOPHY: SAME TESTS FOR DIFFERENT IMPLEMENTATIONS
   Both partition_list and partition_list_dummy_nodes use nearly identical test suites.
   This approach:
   
   a) Verifies both implementations meet the same specification
   b) Makes it easier to compare algorithmic approaches
   c) Catches implementation-specific bugs (like the .next vs .value bug)
   d) Ensures consistency across multiple solutions to the same problem


SUMMARY
=======
Key takeaway: When implementing doubly linked list algorithms, especially partitioning,
carefully manage all pointer assignments (both next and prev), handle edge cases where
one partition may be empty, and test both forward and backward traversals to verify
bidirectional link integrity. The dummy node pattern is elegant but requires careful
handling of the final tail pointer assignment.

9. BINARY SEARCH TREE DISPLAY AND VISUALIZATION
   Implementation tip for displaying tree structure:
   
   a) Use ASCII box-drawing characters: ├──, └──, │
   b) Maintain prefix strings for nested indentation
   c) Determine "is_tail" to choose correct connectors
   d) Collect children before printing to properly handle both left and right subtrees
   
   Pattern: For each node, print with proper connector, then recursively print
   children with adjusted prefix strings.


10. STACK OPERATIONS AND SORT_STACK ALGORITHM
    Stack sort using auxiliary stack (staging):
    
    a) Maintain two stacks: input and staging
    b) Move smaller elements back to input if needed
    c) Time complexity: O(n²) in worst case
    d) Space complexity: O(n) for auxiliary stack
    
    LIFO (Last-In-First-Out) property ensures correct ordering with proper logic.


11. QUEUE OPERATIONS - FIFO BEHAVIOR
    Queue maintains first and last pointers:
    
    a) Enqueue: Add to tail (self.last)
    b) Dequeue: Remove from head (self.first)
    c) Always update length consistently
    d) Handle single-element case where first == last
    
    Key difference from Stack: Positional access (first vs last) determines order,
    not insertion/removal pattern.


12. LINKED LIST REVERSAL TECHNIQUES
    Three reversal approaches:
    
    a) Three-pointer approach (traditional):
       - Track previous, current, and next nodes
       - Reverse links by setting current.next = previous
       - Update prev and current before next is lost
    
    b) Reverse between indices:
       - Use dummy node to handle head changes
       - Track nodes before and after reversal range
       - Use move pattern to reverse in-place
    
    c) Swap pairs:
       - Use dummy node to simplify head updates
       - For each pair: prev.next = second, first.next = second.next, second.next = first
       - Move prev and curr pointers correctly after each swap


13. TWO-POINTER TECHNIQUES IN LINKED LISTS
    Fast and slow pointers for:
    
    a) Find middle node: slow moves 1 step, fast moves 2 steps
       - When fast reaches end, slow is at middle
       - Handles both even and odd length lists
    
    b) Detect cycle: if fast == slow, cycle exists
       - Fast moves 2 steps, slow moves 1 step
       - Must check for None before accessing next.next
    
    c) Find kth from end: 
       - Move fast pointer k-1 steps ahead
       - Then move both until fast reaches tail
       - slow pointer is at kth from end


14. DOUBLY LINKED LIST PALINDROME CHECKING
    Forward and backward traversal from opposite ends:
    
    a) Compare forward (head) and backward (tail) simultaneously
    b) Move forward.next and backward.prev inward
    c) Loop until meeting at middle (mid-field comparisons)
    d) Works for both even and odd length lists
    e) Time: O(n), Space: O(1)


15. DUPLICATE REMOVAL IN LINKED LISTS
    Two approaches:
    
    a) Set-based (leet_code_remove_duplicates):
       - Use set to track seen values
       - More efficient for large n
       - Time: O(n), Space: O(n)
    
    b) Nested loop (leet_code_remove_duplicate_nested):
       - Compare each node with all following nodes
       - Remove duplicates by skipping
       - Time: O(n²), Space: O(1)
       - Useful when space is critical


16. BINARY CONVERSION IN LINKED LIST
    Each node value (0 or 1) represents a bit:
    
    a) Calculate length first
    b) Traverse and compute: value += (2^(length-1)) * node.value
    c) Decrement length for each node processed
    d) Final value is the decimal equivalent
    
    Alternative: Use bit shifting for cleaner code


17. GET METHOD OPTIMIZATION IN DOUBLY LINKED LIST
    Index-aware traversal:
    
    a) If idx < length/2: traverse from head
    b) Else: traverse from tail (backward)
    c) Reduces average traversal by half
    d) Critical optimization for large lists
    
    Trade-off: Slightly more complex code for O(n/2) vs O(n) performance.


18. SWAP PAIRS BUG FIX - IMPORTANCE OF TESTING
    Original bug in swap_pairs implementation:
    
    Issue: Head pointer was incorrectly reassigned
    Root cause: Incorrect logic when updating head from dummy node's next pointer
    
    Fix: 
    - Use dummy.next to access new head properly
    - Update tail by traversing to the actual last node
    - Verify both head and tail point to real data, not dummy
    
    Learning: Implementation bugs often surface only with comprehensive test coverage.
    Unit tests for edge cases (empty list, single node, pair counts) catch such bugs.


19. LINKED LIST OPERATIONS - COMMON PATTERNS
    Successful patterns across implementations:
    
    a) Dummy node for simplifying head changes
    b) prev = curr; curr = curr.next pattern for traversal edits
    c) Always maintain length consistently
    d) Test boundary cases: empty list, single element, two elements
    e) Verify both forward and backward connectivity (doubly linked)
    f) Clear node pointers (node.next = None) after removal


20. BST PROPERTY MAINTENANCE
    When inserting into BST:
    
    a) All left subtree values < parent value
    b) All right subtree values >= parent value
    c) Duplicates typically go right (implementation-dependent)
    d) Property verification: recursive check of min/max bounds
    
    Importance: Property verification in tests ensures algorithm correctness.
